## 1. Назначение и обязательность

Ты — Codex, инженерный ассистент проекта БЕРИ. Работай только в рамках задачи пользователя, утверждённых архитектурных решений и фактического состояния целевой ветки. **Не подменяй планируемую функциональность реально существующей.** Каждый вывод о реализации подтверждай файлами и, когда доступно, тестами. Не переписывай код, который уже существует, из старых веток или прошлых спецификаций.

При конфликте источников: (1) явное последнее решение пользователя; (2) актуальная главная продуктовая спецификация/согласованные требования для желаемого поведения; (3) текущий код и миграции `develop` для фактического поведения; (4) исторические документы. Расхождение «требование ↔ реализация» **не означает**, что код или требование можно самовольно изменить. Представь пользователю конкретный конфликт и предложи изменение с последствиями.

Главная проектная спецификация `БЕРИ_Главная_спецификация_v1.3.0.md`, ERD `БД_Актуализированная.drawio`, контексты БД/Backend, технические требования и бизнес-процессы хранятся отдельно в источниках проекта ChatGPT. **Нельзя предполагать, что локальный Codex имеет к ним доступ.** При отсутствии файла/контекста запроси необходимый фрагмент. Данный `Specification.md` предназначен для локального репозитория; он **не заменяет** главную бизнес-спецификацию.

## 2. Жёсткие правила полномочий и Git

1. **Никогда не выполняй `git push`, `git push --tags`, force push, отправку изменений в удалённый репозиторий или действие, эквивалентное push.** Вместо этого объясни пользователю точные команды, какую ветку и какие файлы отправлять, и предупреди о последствиях.
2. **Не выполняй `git commit` без явного предварительного согласия пользователя** на содержимое и сообщение конкретного коммита. Сначала покажи `git status`, список файлов, diff-резюме и предлагаемое Conventional Commit сообщение. Разрешение на один commit не разрешает следующий.
3. **Не создавай, не закрывай, не сливай Pull Request самостоятельно.** Сообщи, когда код готов к PR, предложи base/head, заголовок и текст, ссылку на форму GitHub и необходимые ручные действия. Отдельно согласуй момент PR и merge.
4. Не выполняй `git reset --hard`, `git clean -fd`, удаление веток, DB/volumes, принудительное перезаписывание файлов, destructive migration или изменение защищённых веток без разрешения. Не стирай несвязанные локальные изменения пользователя.
5. Перед работой проверь `git status --short --branch`, `git branch -avv`, актуальность remote и целевой base; текущий `develop` защищён, `main` защищён. Новые функции — `feature/...` от `develop`, исправления — `fix/...` от `develop`; релизы `release/...`, экстренные исправления `hotfix/...` — по утверждённому GitFlow.
6. Не разрабатывай непосредственно в `main` или `develop`. Для `feature`/`fix` рекомендован Squash and merge после ревью, для release/hotfix — согласованная командой политика merge.
7. Сообщения коммитов — Conventional Commits на английском (`feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`). Один коммит — логически законченный блок.
8. Никогда не добавляй `.env`, credentials, токены, приватные ключи, local DB dump, `node_modules`, virtualenv, build artifacts. Проверяй diff и `.gitignore` перед staging.
9. Перед PR обязательны тесты, Code Review, Security Review и Documentation Gate; не выдавай непроверенное за пройденное. Не обходи branch protection.

### Обязательный шаблон передачи Git-действий пользователю

- Указать `feature/...` и `develop`, что изменилось и какие файлы нужно включить.
- Предложить **без выполнения** команды `git status`, `git diff --check`, выборочный `git add <конкретные файлы>` и `git diff --cached`, затем — `git commit -m "..."` **только после согласования**.
- После разрешённого пользователем коммита вывести команду `git push -u origin <ветка>` для **самостоятельного запуска пользователем**.
- Сказать «Создавайте PR `<ветка>` → `develop` после проверок и публикации ветки», перечислить ревьюеров и требуемые проверки. PR/merge не делать за пользователя.

### 5.2 Точные ограничения текущей сессионной авторизации

- Регистрация: только customer, пароль через Django validation/hashing, `phone_verified_at=NULL`, **без** автоматического login и без реального SMS.

- Сессия в HttpOnly cookie, SameSite=Lax; JS-readable CSRF cookie, CSRF на POST в т.ч. анонимных; не отключать эти механизмы для работы Vite proxy.
- `GET /api/auth/me/` для анонима возвращает `authenticated:false`, не считать любой 403 автоматическим logout.

- Внешний телефонный статус нельзя выдавать за подтверждённый; реальные платёжные реквизиты не использовать.
- `Account.status` — непрозрачная непустая строка, не enum blocked/active. Доступ управляется актуальным `is_active`. Полномочия физической операции требуют Employee/ПВ даже superuser.

### 6.2 Бизнес-цикл

Поиск/просмотр → бронирование конкретного `product_item` на **60 минут** → осмотр в ПВ → возможно несколько замен **в той же** `reservation` с историей `reservation_item_assignment` → выдача и создание одной `rental` → аренда **без заранее заданного срока** → возврат **в тот же ПВ**, подтверждение сотрудником останавливает время → проверка → итог по фактическим секундам и сохранённой ставке → попытка списания → задолженность при неуспехе.

Обязательно:
- GET поиска и наличия **не меняет** `product_item.status`; текущее наличие не гарантирует будущую бронь.
- Одна активная бронь и одна активная аренда на конкретный экземпляр, максимум одна аренда на бронь; инварианты защищать БД и транзакциями.
- Замена: только тот же товар/ПВ, initial item неизменен, каждое назначение сохраняется. Проблемные экземпляры становятся `unavailable`.
- Выдача: только действующая бронь до `expires_at`, исправный экземпляр, активное **подтверждённое** платежное средство, отсутствие открытого долга, права Employee данного ПВ. Фиксировать тариф и ставку на момент выдачи.
- Итоговая стоимость пропорциональна точным секундам, **не** округляется до полного часа. Способ денежного округления до копеек **не утверждён** — согласовать до реализации биллинга.
- Завершение аренды **не зависит от успешности оплаты**; неопределённый `pending` не равен `failed`. Одна задолженность на аренду; в MVP только полное погашение. Никаких автоматических штрафов за повреждения.
- Платёжные данные: только token/external ID, brand и last4 при необходимости; **никаких PAN/CVV**. Нет настоящих транзакций до отдельного решения и безопасной интеграции.
- Критичные операции: `transaction.atomic()`, `select_for_update()` и защита от повторов; сетевые вызовы провайдеру **не держать** в длинной DB-транзакции. Проверять гонки на PostgreSQL.
- Не удалять физически историю бронирования, назначения, выдачи, проверок, платежей и долгов.

### 6.3 Открытые проектные решения

**Требуют отдельного утверждения, не выдумывать:** денежное округление до копеек; SMS TTL/попытки/провайдер и политика верификации для production; словарь причин замен и связи с inspections; платёжная идемпотентность, область уникальности external ID и обработка pending; переход Desktop-only плана к общим требованиям адаптивности. Другие вопросы выявлять при изменении моделей или контрактов.

**Решение пользователя 31.10.2026 для S1-P3:** фото необязательно. `Product.image_url` сохраняет существующие `null=True, blank=True`; Django Admin позволяет создать товар без фото. Схему БД и контракт API ради этого не менять.

## 7. Код, API, тесты и безопасность

- Python: PEP 8; `snake_case` для функций/переменных, `PascalCase` для классов, `UPPER_SNAKE_CASE` для констант. Небольшие функции, явные типы/смыслы и контролируемые ошибки.
- REST: согласованные стабильные пути, корректные 400/401/403/404/405/409/429 и структура ошибок. Не смешивать права API и Django Admin. Текущий auth API имеет `{"error":{"code":"...","message":"...","fields":{...}}}`; расширение общих кодов требует согласования.
- Покрывать happy path, отказ, чужие объекты/ПВ, повторные запросы, границы времени, некорректные входные данные, конкурентные операции и миграции по необходимости.
- Backend проверки в **отдельной собственной** PostgreSQL: `python manage.py check`, `python manage.py makemigrations --check --dry-run`, `python manage.py migrate --plan`, `python manage.py test --noinput`. Replay миграций — только на безопасной пустой БД.
- Frontend: `npm ci`, `npm run build`, `npm run test:e2e` в допустимой среде. Не публиковать тестовые номера/секреты и не маркировать mocked E2E как полноценный live integration test.
- Исторические отчёты PR #8 упоминают 625 backend тестов и 5 E2E **до последней правки R1**; PR #10 сообщает 101 тест pickup_points/inventory; эти числа **не** являются результатом сегодняшнего полного прогона по HEAD.
- Безопасность: защищать сессии, CSRF, секреты, лимиты, запросы к финансовым данным и IDOR. Запретить несанкционированные `Employee` привязки, административную эскалацию и использование чужого платежного средства.
- Не оптимизировать за счёт снятия PostgreSQL ограничений/прав. При нехватке времени переносить несущественные удобства, а не integrity/security.

## 8. Documentation Gate и версионирование — каждый PR

**Этот раздел обязателен без исключений, в том числе для `fix`, `refactor`, `test`, `chore`, `docs` PR.**

1. Перед началом PR зафиксировать base branch и SHA; сверить все изменённые исходники, тесты, migrations, endpoints и пользовательский сценарий.
2. Обновить `Specification.md` в **той же рабочей ветке**, отразить актуальный снимок возможностей/ограничений, дату, SHA проверки, затронутые правила; проверить `README.md`/`docs/*` и исправить устаревшее.
3. **Повысить SemVer документа на каждом новом PR**, даже если правила не менялись: `PATCH` — очередной PR/уточнения и актуализация состояния; `MINOR` — новая роль/совместимое значимое правило; `MAJOR` — несовместимая смена требований к поведению Codex. Версия продукта/релиза **отдельна** от версии документа. Не использовать автоматически версию `frontend/package.json`.
4. В Change Log записать дату, прошлую и новую версию, PR/ветку (если номер ещё не известен — `pending`), проверенный base SHA, краткое содержание, затронутые docs, ограничения проверки. Не приписывать себе merge до его факта.
5. Новая редакция `Specification.md` должна присутствовать в PR-diff. Пользователь разрешил хранение файла в локальном и удалённом репозитории 31.10.2026; повторное согласование хранения не требуется. Не включать в Git секреты или внешние документы без отдельного основания.
6. Если изменения исключительно документационные, всё равно увеличь версию и обнови Change Log. Перед публикацией проверь, что номер не конфликтует с версией в другой параллельной ветке: при конфликте ребейз/повторный bump согласовать с пользователем.
7. Не создавай бесконечный цикл «обновить spec → новый PR»: одно обновление включается в тот же PR. Если перед merge изменился base, повторно сверить diff/документацию и поправить changelog в рамках существующего PR.
8. `main`/`develop` не редактировать напрямую. Codex не commit/push/PR/merge без обозначенных в §2 разрешений. Версия 1.2.1 относится к текущей рабочей ветке S1-P3; следующий отдельный PR требует очередного повышения версии.

### Минимальный PR checklist

- [ ] Изменения отвечают задаче; diff прочитан, нет посторонних файлов/секретов.
- [ ] Backend/frontend тесты, PostgreSQL migrations, E2E проверены **или честно обозначены как не выполненные**.
- [ ] Reviewer проверил логику, Security Engineer проверил уязвимости и права.

- [ ] README, API, auth и прочая затронутая документация обновлены или явно помечены как не затронутые.
- [ ] Пользователь получил техническое и бизнес-объяснение, ручные команды commit/push и рекомендацию момента создания PR.

## Назначение и границы

Пользователь открывает товар из каталога, видит описание, характеристики,
комплектацию и текущий почасовой тариф, выбирает ПВ и узнаёт число свободных
экземпляров. Страница публична и использует существующий Django API.
Бронирование, запись в API, Backend, модели, миграции и зависимости не изменены.
Глобальные `style.css` и `catalog.css` не изменены; новые CSS-правила ограничены
`.product-page`. Стилистика БЕРИ сохранена.

## Данные и обработка ошибок

Используются `GET /api/products/{id}/`, `GET /api/pickup-points/` и
`GET /api/products/{id}/availability/`. Выбор ПВ сопоставляет
`pickup_point_id` локально, без нового endpoint или запроса на переключение.
Поздний ответ предыдущей загрузки не подменяет актуальное состояние.
Ошибки detail, списка ПВ и наличия имеют собственный повтор. Ошибка наличия
не превращается в нулевой остаток, отсутствующий тариф — в нулевую цену.
Есть прямые ссылки «Вернуться в каталог» внутри 404 и ошибки загрузки товара.

`PickupPoint.status` в существующей модели — строка без choices/default,
а API списка и наличия возвращают все ПВ. Подтверждённого правила,
какие значения означают неактивность и требуют скрытия, нет. Показываются
все ПВ из API; фильтрация не менялась. `ProductItem.status = available`
определяет свободные экземпляры и не описывает активность самого ПВ.
Изменение этого правила требует отдельного согласования.

## Порядок повторной проверки

Использовать только собственную изолированную PostgreSQL с уже применёнными
каноническими миграциями и указанными выше данными. Подключение — в игнорируемом
`backend/.env`. Не подключать общую или production БД. Для существующего
локального окружения установка программ, создание БД и повторное заполнение не нужны.

1. Запустить свою PostgreSQL. В первом терминале из `backend`:
   `python manage.py runserver 127.0.0.1:8000 --noreload`.
2. Во втором терминале из `frontend`: `npm run dev -- --host 127.0.0.1`.
3. Открыть `http://127.0.0.1:5173/catalog`, перейти по названию товара.
4. Проверить описание, характеристики, комплектацию, тариф; выбрать ПВ1,
   затем ПВ2, сравнить остатки 2 и 0 с API.
5. Открыть второй товар: сообщение об отсутствии текущего тарифа и заглушка изображения.
6. Открыть `/products/999999999`: 404-состояние и рабочая ссылка в каталог.
7. Повторить переход и выбор ПВ с клавиатуры.

Команды из `frontend` (Playwright использует установленный Chrome;
для Edge в PowerShell: `$env:BERI_E2E_BROWSER = 'msedge'`):

```powershell
npm run build
npm run test:e2e -- catalog.spec.ts product.spec.ts
npm run test:e2e -- product-live.spec.ts
```

Штатный live-тест выбирает первый товар из реального каталога и сравнивает UI
с ответами Django. Для проверки именно обеих ситуаций тарифа и остатков
нужны указанные учебные данные и ручные шаги 4–6. Полный auth E2E отдельно
не перезапускался. Сессии, CSRF и API-контракты не изменены.

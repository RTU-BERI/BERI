## 2. Что реализовано

### BERI-204-A — создание бронирования

На существующей `/products/:id` добавлен блок бронирования. Один существующий
select ПВ передаёт выбор форме; URL `?pickup_point={id}` сохраняет контекст.
Новый независимый select, выбор экземпляра, календарь и длительность аренды
не добавлялись.

Подтверждение показывает товар, фото/заглушку, ПВ и адрес, тариф и условия
60-минутного удержания. Без ПВ или тарифа подтверждение недоступно. Анониму
предлагается существующий login; после входа восстанавливается допустимый
внутренний URL. Для employee клиентская операция недоступна.

POST использует общий API-клиент, session и CSRF. UUID создаётся для новой
операции; сетевая ошибка, 5xx или невалидный успешный ответ сохраняют его для
повтора. Синхронный pending-флаг и disabled-кнопка предотвращают двойную отправку.
Во время отправки выбор ПВ блокируется. Неизвестная операция сохраняется в
памяти при внутренних переходах, не заменяется незаметно операцией другого ПВ.
Контекст очищается при смене аккаунта/выходе. Он не хранится в localStorage или
sessionStorage. После полного reload при неизвестном результате следует сначала
проверить собственную историю, прежде чем намеренно создавать другую бронь.

409 различаются по фактической причине: известная нехватка/конкурентное
назначение экземпляра получает согласованное сообщение, UUID/истечение и другие
конфликты не называются «товар занят». Ошибка сессии вызывает проверку `me`;
403 сам по себе не выполняет logout. Наличие после создания обновляется GET,
локального списания экземпляров нет.

Результат содержит фактический статус, ID, товар, ПВ, серверный expires_at,
countdown и переход к истории. Завершённая бронь при идемпотентном повторе
не выдаётся за новую активную.

### BERI-204-B — история и отмена

Новый маршрут `/my-reservations`, ссылка в существующей навигации для клиента.
GET получает только собственный список. Отображаются товар/заглушка, ПВ/адрес,
создание, срок и четыре статуса: «Активно», «Отменено», «Истекло», «Выполнено».
История не удаляется. Каталог и справочник ПВ загружаются один раз, в том числе
при проверке React StrictMode, и сопоставляются по ID. Отсутствие справочника
оставляет карточку с ID и доступными данными.

Отмена имеет подтверждение с безопасным действием «Оставить бронирование».
До ответа успех не показывается. После 204 список обновляется GET; 409/404
тоже вызывают сверку. Неактивные/локально просроченные записи не предлагают
новую отмену. Сервер остаётся единственным источником состояния и полномочий.
Поздний ответ после logout не восстанавливает приватный список.

### Countdown и время

Срок берётся из expires_at, а не из новых 60 минут после ответа. Валидный HTTP
Date служит приближённой серверной опорой с учётом сетевого времени;
performance.now защищает интервал от изменения часов устройства. Без Date
интерфейс честно показывает ориентировочный расчёт по устройству.

На нуле выполняется ограниченная проверка серверного списка: один автоматический
GET на бронь/срок, параллельные запросы объединяются. Если сервер всё ещё
возвращает active, отображается ожидание подтверждения. Самостоятельного
перехода expired нет. Focus/visibility и ручное обновление повторяют сверку.
Завершённые записи не запускают countdown, интервалы и обработчики очищаются.

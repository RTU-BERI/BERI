## Что реализовано

`/employee/reservations` загружает доступные брони ПВ и показывает номер,
товар/ПВ по ID из API, статус и срок. Есть загрузка, пустой список, ошибка
и обновление. Телефон клиента из ответа исключён из состояния страницы.

`/employee/reservations/:reservationId` загружает актуальное назначение и
историю осмотров. Положительный результат требует подтверждения состояния
и комплектности. Запись отправляет expected_assignment_id из последнего GET.

Минимальная форма проблемы фиксирует одну проблему состояния — повреждение,
неисправность или другое — с описанием и причиной до 30 символов. Комплектность
подтверждается отдельно. Запрос замены не передаёт replacement_item_id,
поэтому Django выбирает другой допустимый экземпляр того же товара/ПВ.
После замены новое назначение загружается заново и требует своего осмотра.

Отмена при отсутствии замены требует отдельного согласия сотрудника.
Без согласия completion_reason отсутствует и сервер возвращает 400 с полным
откатом. При согласии передаётся причина «Нет свободной замены», после чего
сервер может отменить бронь в той же транзакции. Busy-конфликт 409 сохраняет
свою семантику. История отражает фактический результат GET.

После положительного осмотра сотрудник подтверждает фактическую передачу
товара и нажимает выдачу. POST issue передаёт только актуальный assignment ID.
Успех показывает начало аренды и серверное время. При возврате в список он
загружается заново и отражает статус fulfilled.

Истёкшая/отменённая/выданная бронь отображает историю. Допуск по реальному
времени, долгам, платёжному средству, тарифу, правам, состоянию экземпляра
и создание Rental выполняет Django. В браузере нет вычисления этих условий
или прямого изменения статуса экземпляра.

POST защищён синхронным ref-флагом и disabled-кнопками. Ошибка не запускает
автоматический повтор. После 409 либо неизвестного результата записи нужна
явная загрузка GET. Найденный сохранённый осмотр/fulfilled исключает повторную
запись через форму. Поздний ответ предыдущей загрузки игнорируется. При смене
брони/аккаунта компонент размонтируется и его данные не восстанавливаются.

Понятные сообщения предусмотрены для 400, 401/403 (права, сессия, CSRF),
404 (включая чужой ПВ), 409 и сетевых/серверных ошибок. Общий клиент с cookie
и CSRF используется без изменений. В App добавлены только import, отдельный
Employee entry и маршрут. Изменения PR #18 в навигации, login returnTo,
общем клиенте и клиентских страницах проверены в объединённой копии.

## Границы review и интеграции

Выполнены последовательные Code/Security self-review и Documentation Gate.
Проверены PII, same-origin/CSRF, stale ответы/назначения, повторное нажатие,
сброс данных при уходе, отсутствие секретов и серверных изменений в diff.
Независимое reviewer approval не заявляется. До merge нужен командный review
и разбор известного backend failure по правилам проекта.

Минимальная форма поддерживает одну проблему состояния. Недокомплектность
требует product_component_id и количества. Публичный detail не выдаёт ID
элементов комплектации, поэтому отдельный редактор недокомплектности не добавлен.
История полученных осмотров с таким результатом отображается. Возврат,
расчёт, оплата и мобильная вёрстка остаются следующими задачами.

Перед публикацией повторно проверяются статусы #18/#19 и origin/develop.
Если они слиты в процессе этой работы, feature обновляется и проверки
повторяются. Если PR остаются открыты, текущая интеграционная проверка не
выдаётся за запуск на merged develop. После будущего merge #19 нужны обновление
ветки от develop и повтор live-приёмки. Самостоятельное ожидание будущего merge
или автоматическое наблюдение этой задачей не настроено.

## Запуск и повтор проверки

Запустите PostgreSQL, Django и Vite по README/auth. Для полного сценария
нужен backend с issue из #19. Создайте синтетического Employee с профилем ПВ
и Django permissions. Список требует accounts.view_employee, история —
rentals.view_inspection, осмотр — rentals.add_inspection, замена дополнительно
rentals.add_inspectionproblem, reservations.change_reservation и
reservations.add_reservationitemassignment, выдача — rentals.add_rental,
reservations.change_reservationitemassignment и inventory.change_productitem.
Сервер повторно проверяет все права. is_staff сам по себе их не заменяет.

В браузере войдите как сотрудник, откройте «Выдача товаров», выберите бронь,
проверьте комплектность/состояние и сохраните осмотр. Для замены выберите
«Обнаружена проблема состояния», заполните описание и причину, при необходимости
разрешите отмену при отсутствии замены. Новый экземпляр осмотрите заново.
Перед фактической выдачей отметьте подтверждение передачи.

Для mocked-проверок из frontend с запущенным Vite

```bash
npm ci
npm run build
BERI_E2E_BROWSER=msedge npm run test:e2e -- e2e/employee.spec.ts
```

Live-тест получает путь к приватной JSON-фикстуре через
BERI_EMPLOYEE_LIVE_FIXTURE. Формат включает password, users с синтетическими
customer/employee/colleague/restricted и bookings с UUID healthy/replace/
no_replacement/stale/expired/foreign. Каждый прогон требует свежих броней.
Для replace/stale подготовьте по два подходящих экземпляра, для no_replacement
один. Коллега имеет права своего ПВ, restricted — профиль без прав.
Клиенту для выдачи нужен допустимый тестовый метод и текущий тариф по #19.
Без указанной переменной пять live-тестов явно skipped.

Готовый seed запускается из backend через Django shell после migrate. Он
требует DEBUG, BERI_LIVE_ISOLATED=1, новую пустую локальную PostgreSQL с именем
beri_s2p6* и ещё не существующий приватный путь BERI_EMPLOYEE_LIVE_FIXTURE вне
репозитория. Создаёт синтетические роли, товары, брони, тарифы и учебный метод
командой #19. Существующие данные не удаляет. Нужен backend с #19.

```bash
export BERI_LIVE_ISOLATED=1
export BERI_EMPLOYEE_LIVE_FIXTURE=/absolute/private/path/employee-fixture.json
python manage.py shell -c "exec(open('../frontend/e2e/employee_live_fixture.py', encoding='utf-8').read())"
```

```bash
BERI_E2E_BROWSER=msedge BERI_EMPLOYEE_LIVE_FIXTURE=/path/outside/repo/fixture.json \
  npm run test:e2e -- e2e/employee-live.spec.ts
```

## Объяснение от моего имени

Я сделала экран сотрудника пункта выдачи. Он показывает доступные мне брони
и историю осмотров. Я могу сохранить положительный осмотр или описать проблему
и попросить сервер подобрать замену. После замены я осматриваю новый экземпляр.
После положительного осмотра я подтверждаю передачу товара клиенту.

Моя React-страница отвечает за формы, запросы, состояния и понятные сообщения.
Django проверяет сотрудника, ПВ, срок брони, назначение и условия выдачи.
Он меняет состояние в транзакции и создаёт аренду. ID назначения приходит
с сервера, поэтому устаревшая форма получает конфликт и предлагает обновление.
Кнопки блокируют повторную отправку, а после потери ответа страница сначала
читает актуальную историю.

Я проверила полный сценарий с настоящим Django и отдельной учебной PostgreSQL.
Сетевые ошибки и двойное нажатие дополнительно проверила браузерными тестами
с подменёнными ответами. Совместную работу с клиентской страницей бронирования
проверила во временной копии проекта.

## Что реализовано

**BERI-301-A:** действующий Employee своего ПВ с разрешениями фиксирует предвыдачной
осмотр только активной, не просроченной брони. Inspection и полный список
InspectionProblem записываются одним событием. Флаги сверяются с проблемами;
компоненты принадлежат тому же товару, сумма недостачи не больше комплектации.
Время/Employee/родители/тип осмотра определяет сервер. Подтверждение клиента
не подделывается: customer_confirmed_at=NULL. Rental/выдача/Frontend не добавлены.

**BERI-301-B:** проблемный осмотр записывается только вместе с разрешением
ситуации. При замене старый item становится unavailable; его назначение закрывается,
новый available item того же товара/ПВ становится reserved, создаётся Assignment
с sequence_no+1, Employee и причиной. initial item, created_at и expires_at не меняются.
Можно выполнить несколько последовательных замен, затем осмотреть новый item.
Ранее назначенные этой брони items повторно не используются.

Если автоматический подбор не нашёл кандидата или клиент отказался от замены,
сотрудник может отменить бронь в той же транзакции только с явно переданной
причиной отмены≤50. Старый item остаётся unavailable, last pointer сохраняется,
Assignment закрывается. Без причины —400 и полный rollback. Явно недоступный
выбранный item или временно занятый lock —409, не повод для отмены.

Этот контракт, свободная причина замены≤30 без enum, один неизменяемый результат
осмотра на назначение и правила повторов утверждены пользователем перед реализацией.
Согласованные ранее проверки флагов/проблем и истории этапа9 сохранены; прежний
удалённый Backend целиком не восстанавливался.

## API для S2-P6

| Метод | URL | Назначение |
|---|---|---|
| GET | /api/employee/reservations/{uuid}/inspections/ | Контекст брони, expected_assignment_id и история осмотров |
| POST | тот же inspections URL | Исправный осмотр и точный безопасный повтор |
| POST | /api/employee/reservations/{uuid}/replace/ | Проблемный осмотр + замена либо явная отмена |

Точный JSON/права/ошибки: [API.md](API.md#s2-p4-pre-issue-inspections-and-replacement).
GET выдаёт ID текущего назначения даже до первого осмотра. Возвращает только
доступную сотруднику историю своего ПВ, без customer phone/password/token.
Read-only короткий lock заголовка даёт согласованное состояние назначения.

Write возвращает200 с Inspection, reservation status/initial/assigned item,
assignment_id и sequence_no. Повтор исправного осмотра тем же сотрудником с теми
же валидированными данными возвращает прежний ID/время. Изменение данных/автора,
старый expected_assignment_id и повтор выполненной замены —409 без записи.
Новый осмотр возможен после замены на новом назначении. После успешного осмотра
не допускается переписывание результата того же назначения на проблемный.
История может читаться и после завершения брони; новые записи после T>=expires_at
или terminal status запрещены.

## Права, атомарность и совместимость

Использованы существующие свежие Account/Employee helpers и scoped DRF mixins.
POST inspection требует rentals.add_inspection. Замена дополнительно требует
rentals.add_inspectionproblem, reservations.change_reservation и
reservations.add_reservationitemassignment. GET требует rentals.view_inspection.
Employee профиль, employee account_type, is_active и ПВ обязательны даже
superuser; is_staff сам по себе не даёт доступа и не требуется обычному API.
CSRF/session authentication и глобальные настройки/обработка auth не менялись.
Неизвестные и серверные входные поля отклоняются400, не игнорируются.

Новые writer используют прежний narrow models.Model.save путь, оставляя публичные
save/update/delete/bulk guards нетронутыми. Account→Employee→Product→PickupPoint,
потом Items по PK→Reservation→Assignments→location histories. Product/point NO KEY
UPDATE сохраняют родительские данные и сериализуют осмотры одного товара/ПВ;
это сознательная консервативная граница производительности, не обещание высокой
нагрузки. Item NOWAIT отказывает409 при временном конфликте. Все потенциально
ожидающие row locks взяты до единого серверного aware T и проверки expiry.
Права повторно проверяются внутри транзакции. Код не вводит отдельный протокол
блокировки изменения Group permissions: они перечитываются без старого user-cache.

Осмотр сериализуется с canonical ProductComponent guards: первый осмотр замораживает
весь комплект, включая ещё не упомянутые компоненты. Ни исторические строки,
ни состав после осмотра поддерживаемый API не редактирует.

Сервисы PR15/16 сохранены побайтно: create/is_active/expire/cancel. Отмена/истечение
освобождают только последнее reserved назначение; старые unavailable не становятся
available. При гонке close, заранее прочитавшего старый pointer, с выигравшей заменой
возможен контролируемый отказ с rollback; обновлённый вызов/следующий expiry sweep
обработает новую запись. Автоматические retries и scheduler не добавлялись.

Без новых SQL constraints/триггеров межтабличные гарантии обеспечиваются этими
сервисами и существующими guards. Произвольный raw SQL остаётся обходом; новая
SQL уникальность Inspection/assignment не обещается, модели/миграции неизменны.

## Как проверить на своей отдельной БД

1. Только в изолированном PostgreSQL окружении задать DB_* и применить существующие
   миграции. Основную beri не использовать для тестов. Запустить check,
   makemigrations --check --dry-run и test apps.rentals.test_pre_issue --noinput.
2. Подготовить Product/комплектацию/ПВ, два available item через существующий
   inventory.create_item, Customer и Employee своего ПВ с перечисленными правами.
3. Клиентом POST /api/reservations/ создать бронь. Сотрудником с session/CSRF
   получить GET inspections и expected_assignment_id.
4. Для исправного сценария отправить два одинаковых POST inspections: ID/время
   совпадают. Изменённый comment должен дать409.
5. Для проблемного сценария использовать отдельное ещё не осмотренное назначение:
   POST replace с problem/reason и optional candidate. Проверить old unavailable,
   new reserved, sequence+1, неизменность initial/expiry. Повтор старого запроса409.
6. Получить новое назначение GET, повторить проблемную замену либо исправный
   осмотр. Cancel/expiry в конце не должны освобождать прежние повреждённые items.
